# 最小支付 MVP：产品调研与多方评审结论

**评审结论：有条件通过。** 仅在下文“上线阻断项”全部关闭后，才进入真实收款开发；在此之前可完成原型、服务端骨架和支付沙箱联调。

## 1. 产品经理结论：将 MVP 收敛为一个闭环

### 目标与定位

目标用户是使用桌面环境进行**编程练习、模拟面试复盘和个人学习**的中文开发者/求职者。首期售卖的是“合规的托管云端练习服务与额度”，而不是开源客户端本体，也不面向真实面试、考试或规避监考场景。

首要待验证假设：用户在完成一次练习后，愿意为免配置密钥、托管模型额度与复盘便利付费。

### MVP 范围

| 纳入首发 | 明确不做 |
| --- | --- |
| 登录（邮箱验证码或 OAuth 二选一） | 支付宝、银行卡、国际收款 |
| 一个固定期商品：`Pro 30 天` | 自动续费/代扣、优惠券、分销、多套餐 |
| 一个渠道：微信 Native 扫码支付 | 自助退款、发票自动化、多设备共享 |
| 订单查询、服务端权益发放、基础运营查询 | 加油包、复杂用量运营、推送/深链强依赖 |
| AI 网关的额度校验与扣减 | 客户端本地计量或仅 UI 限制 |

微信支付官方将 Native（扫码）支付列为适用于 PC 网站的场景，符合桌面端的最低集成成本；支付宝电脑网站支付保留为支付漏斗验证后的 P1 备选。[微信支付扫码支付接入指引](https://pay.wechatpay.cn/guide/qrcode_payment.shtml) [支付宝网页/移动应用接入入口](https://open.alipay.com/module/webApp)

### 最小购买路径

```mermaid
flowchart LR
  A[完成一次练习 / 额度将尽] --> B[解锁 Pro]
  B --> C[登录并查看单一商品]
  C --> D[显示价格、权益、退款与协议]
  D --> E[生成微信支付二维码]
  E --> F[手机扫码付款]
  F --> G[渠道异步通知验签]
  G --> H[服务端幂等开通权益]
  H --> I[客户端刷新订单与权益]
```

付款二维码展示商品、总价、订单号与 15 分钟倒计时。客户端每 3 秒查询一次订单（最多 5 分钟）；应用退出、网络中断或关闭浏览器不影响订单，重新登录后仍能同步最终权益。前端回跳或“支付成功”页面只触发刷新，不能开通权益。

### 首期体验与指标

- 套餐页须在首屏回答“买什么、多少钱、何时生效”，并链接服务协议、隐私政策、退款规则与客服联系渠道。
- 成功页显示服务端确认的权益、到期日与客服订单号；本地 BYOK 功能继续可用。
- 记录漏斗：购买曝光 → 点击 → 登录 → 建单 → 扫码 → 支付成功 → 权益发放；另监控验签失败、已支付未发放、退款/投诉和合规举报。
- 技术 SLO：已支付订单 2 分钟内 `fulfilled` ≥ 99.5%；重复通知重复开通 = 0；支付后重启权益恢复 = 100%。商业转化率不预设，先以合规内测数据设定扩张门槛。

## 2. 最小可售技术方案

现有项目是 Electron 客户端，未具备账号、订单或服务端能力。MVP 新增一个单体后端（认证、商品目录、结算、微信适配器/Webhook、权益、AI 网关）和 PostgreSQL；不拆微服务。

### 关键边界

- Electron 仅展示商品、二维码和权益；支付商户私钥、证书、验签密钥和最终价格只在服务端。
- 后端创建订单时按服务端商品目录锁定 `amount_fen`，金额均为整数分；写请求携带 `Idempotency-Key`。
- 渠道 Webhook 必须验签、持久化、按事件去重，再异步幂等发权益。支付成功与权益已发放是不同状态。
- 托管模型额度只有通过 AI 网关计量才可收费交付；若保持用户自带 API Key（BYOK）直连，会员仅能售卖不依赖模型消耗的高级功能，不能可靠限制或计量调用额度。
- 支付页面不嵌入不受控第三方 WebView。主进程只允许 `https` 的自有结算域名，通过白名单调用外部浏览器；令牌进入系统钥匙串/`safeStorage`，不进入 Zustand 或 localStorage。

### 最小数据与状态

`users`、`products`、`orders`、`payment_attempts`、`payment_events`、`entitlements` 是首期必需表。订单状态为：`created → pending_payment → paid → fulfilled`，另有 `expired`、`cancelled`、`refunded`；`payment_events(provider, event_id)` 和 `entitlements(source_order_id)` 必须唯一，确保重复/乱序通知不会双开通。

## 3. 防刷：首发可落地的分层策略

防刷目标不是“绝对拦截”，而是在不伤害正常付费用户的前提下，提高攻击成本、限制损失，并让人工能快速处理。首期采用“规则 + 限流 + 审计 + 人工复核”，不采购黑产画像或复杂风控平台。

| 层级 | 首期措施 | 处置 |
| --- | --- | --- |
| 账号与试用 | 邮箱验证；每个账号只可领取一次试用；试用权益到账即记账 | 同一设备/网络短时多账号领取时，暂停试用并要求人工复核 |
| 建单 | 登录后才可建单；用户、设备、IP 分别限流；同一用户同一商品存在未过期订单时复用订单 | 超限返回冷却时间，不反复向渠道创建交易 |
| 支付 | 服务端锁定商品/金额/商户号；支付渠道签名验签、订单号和金额逐项比对；只接官方持牌渠道 | 验签、金额或商户不匹配即拒绝并报警；绝不以客户端成功页开通 |
| 权益 | `source_order_id` 唯一发放；Webhook 事件去重；退款/争议账号即时冻结托管权益 | 已付款未发放走自动补单，避免客服以手工改库处理 |
| AI/转录用量 | 所有托管请求经网关；账号、设备和 IP 三维限流；额度账本按 `request_id` 幂等扣减 | 异常突增时降级/暂停该账号，保留申诉入口；BYOK 不计入付费额度 |
| 运营 | 每日渠道-订单-退款三方对账；记录规则命中、人工结论和申诉结果 | 风险规则按误伤率和拒付/投诉率每周调参 |

### 建议初始阈值（灰度期）

阈值应只作为可配置的起点，并以正常用户分布校准：单 IP 10 分钟内最多创建 5 个订单、同一账号 10 分钟内最多创建 2 个订单、同一设备 24 小时最多领取 1 次试用；同一账号在短时内切换多个设备/IP、连续支付失败或退款后再次高频购买时，进入人工复核队列。不要仅凭设备指纹永久封禁：它应是辅助信号，并遵循最小必要与保存期限。

### 必须避免的错误

- 不采集或保存银行卡号、支付密码、身份证等支付敏感信息；交由官方收银台处理。
- 不把 IP、设备指纹或单个规则命中直接等同于欺诈；要有人工复核、申诉和可撤销限制。
- 不在客户端做额度判断、支付验签或风控决策；这些都可被绕过。
- 不让客服直接修改订单为“已支付”；补单必须关联渠道查询结果、审计人和原因。
- 不把完整 Webhook 载荷、访问令牌、截图或语音原文写入普通日志。

## 4. 多方评审纪要

| 角色 | 结论 | 上线前必须完成 |
| --- | --- | --- |
| 产品经理 | 条件通过：一个商品、一个扫码渠道足够验证闭环 | 确认商品权益、按模型/转录成本倒推价格、埋点口径 |
| 后端/支付架构 | 条件通过：服务端闭环不可省略 | 账号、订单、Webhook 验签幂等、权益、AI 网关、对账补偿 |
| 桌面端 | 条件通过：二维码 + 订单轮询可实现 | 受控外链、令牌安全存储、支付后恢复状态 |
| 安全 | 条件通过 | 密钥不上端、深链不作为成功依据、审计与日志脱敏 |
| 财务/运营 | 待决 | 经营主体、商户进件、退款/发票 SOP、日对账负责人 |
| 客服 | 待决 | 未到账/误购/退款工单流程、订单查询权限、响应时限 |
| 法务/合规 | 一票否决待决 | 商业授权、产品定位/禁止用途、隐私与协议、支付渠道书面确认 |

## 5. 风险与上线阻断项

1. **商业授权：阻断。** 本仓库 LICENSE 为 `CC BY-NC 4.0`，README 也要求商业授权；收费分发前须取得权利人的书面授权。
2. **产品定位与渠道可接受性：阻断。** 当前仓库文案出现屏幕分享隐身、规避检测和在线考试等表述。真实收款前必须完成合规产品重定位、禁止用途条款和渠道/经营主体审核；不应以此类用途宣传或向其提供付费能力。
3. **经营与售后责任：阻断。** 确认经营主体、商户资质、价格、退款、发票、客服与日对账负责人。格式条款中与消费者有重大利害关系的内容需显著提示；数字化商品是否适用无理由退货及具体退款政策须由法务确认。[消费者权益保护法（全国人大）](https://www.npc.gov.cn/WZWSREL3pncmR3Ly9ucGMvLy8vLy8vbGZ6dC94ZnpxeWJoZnh6YS8yMDE0LTAxLzAyL2NvbnRlbnRfMTg3MjQ4OC5odG0%3D)
4. **个人信息：阻断。** 登录、设备标识、订单与支付状态均涉及个人信息处理。上线前发布可访问的隐私政策，做到最小必要、明确告知处理目的/范围/保存期和权利渠道；若存在数据出境，单独完成对应评估与告知同意流程。[网信办个人信息保护问答](https://www.cac.gov.cn/2026-01/09/c_1769688003183197.htm) [数据出境问答](https://www.cac.gov.cn/2026-07/24/c_1786638883119336.htm)
5. **AI 服务治理：阻断。** 服务协议和产品页需明确禁止考试作弊、规避面试/考试监考、冒充和上传保密信息，建立最小规则拦截、人工升级、账号受限、申诉与审计流程。生成式 AI 服务规则要求面向公众提供服务时公开适用人群、场合和用途，并保护用户输入/使用记录。[生成式人工智能服务管理暂行办法](https://www.cac.gov.cn/2023-07/13/c_1690898327029107.htm)
6. **资金与权益一致性：阻断。** 必须通过沙箱和生产前演练：重复/乱序 Webhook、建单重试、伪造客户端成功、支付后杀进程、订单过期、退款、已支付未发权益和日对账差异。支付通知原文需字段白名单、加密和保留期限，避免将完整载荷写入普通日志。
7. **分发渠道：待决。** 若计划在 Mac App Store 发布，解锁应用内数字功能的支付方式需按 Apple 的审核规则单独评估；本方案的外部二维码仅应假定用于官网 DMG/非商店分发。[App Review Guidelines 3.1.1](https://developer.apple.com/app-store/review/guidelines/)

以上为产品与工程风险评审，不替代法律、税务或支付渠道的正式意见。
