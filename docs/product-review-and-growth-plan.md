# offerGet 产品走查、需求评审与增长方案

更新时间：2026-07-30。本文记录产品、技术、运营、客服和风控视角的评审结论；不把未接通的能力表述为已上线。

## 2. 多方评审共识

### 产品经理

先让新用户在一次完整模拟练习里感知价值，再引导购买。体验码是渠道归因工具，不是永久免费通道；每个码应归属批次和投放渠道。

### 技术负责人

后台不能依赖客户端权限。必须服务端鉴权、短时令牌、限速、审计；模型和 SMTP 密钥不能进入安装包或网页。订单的最终状态必须只由可信支付回调写入。

### 运营负责人

最小后台需在不找开发的前提下查看漏斗、生成渠道体验码、核销追踪、查询用户、补偿权益。体验码明文只显示一次，避免后台泄露。

### 财务/客服

真实支付上线前必须定义订单号、金额单位、支付回调幂等、退款、异常订单、权益补偿和对账日报。不能用“手动标记已支付”替代生产支付。

### 风控与合规

需明确产品为练习/学习辅助工具；不应营销为规避考试、面试或屏幕监控。推广素材、落地页和产品场景应采用“模拟面试、学习练习、知识问答”等合规表述。需要隐私政策、服务协议、数据保留与删除说明、投诉邮箱。

## 3. 后台一期（本次实现）

1. 独立后台密码登录，8 小时短令牌，登录失败 IP 限速。
2. 经营看板：用户、今日新增、活跃会话、订单、收入、体验码状态。
3. 用户与权益：搜索、查看试用/语音/可用次卡、在填写原因后人工补发。
4. 体验码：生成 1–100 个、设置有效期和渠道备注、一次性导出明文、后续仅看末四位和兑换人。
5. 订单：只读查看，避免在未接入微信回调时人工篡改支付状态。
6. 审计日志：登录、发码、撤码、补发权益。

入口：`https://你的官网/admin`。生产环境应在服务器 `.env` 配置独立的 `ADMIN_CONSOLE_PASSWORD`，并使用长度不少于 20 位的随机值。为兼容已有部署，未设置时临时使用 `ACTIVATION_ADMIN_SECRET`；不要使用 `APP_SECRET` 登录后台。

## 4. 后台二期与支付上线门槛

1. 微信支付 Native 扫码订单：商户号、API v3 密钥、证书、平台证书轮换。
2. 支付回调：验签、金额/商户订单号校验、幂等发卡、回调日志、主动查单兜底。
3. 退款：原路退款、权益回收策略、人工审核、退款审计。
4. RBAC：超级管理员、运营、客服、财务只读等角色，以及 TOTP 二次验证。
5. 报表：按渠道体验码批次统计注册、激活、付费与留存；模型调用成本与毛利。
6. 合规页：隐私政策、服务协议、退款规则、问题反馈与账户删除入口。

## 5. AI 自动化推广方案

### 目标与漏斗

首个 30 天目标：有效下载 → QQ 登录 → 完成首场练习 → 体验码兑换 → 购买次卡。每个渠道使用独立的体验码批次标签，后台可归因。

### 内容生产自动化（人审后发布）

1. 建立一个内容库：目标人群、真实问题、产品卖点、合规边界、禁用词、案例素材。
2. AI 每周生成：小红书图文 10 篇、知乎回答 5 篇、B 站口播脚本 3 条、社群答疑 20 条、官网 FAQ 变体。
3. 每篇素材固定包含：痛点、模拟练习场景、功能演示、体验码 CTA、隐私/使用边界说明。
4. 将候选内容写入“待审核”队列；运营人员只需勾选、修改、安排发布时间。未经人工确认不得自动公开发帖、群发私信或购买广告。

### 可量化实验

| 实验 | 变量 | 归因方式 | 成功标准 |
| --- | --- | --- | --- |
| 内容角度 | 算法面试 / 英语机试 / 通用表达 | 每篇独立体验码批次 | 登录转化率 |
| 落地页 CTA | 下载后兑换 / 先看演示 | UTM + 批次码 | 下载到登录转化 |
| 价格表达 | 单次练习 / 10 次备考包 | 订单产品码 | 支付转化、客单价 |
| 召回 | 注册未开练的邮件 | 用户分群、退订 | 首练率，投诉率 |

### 自动化技术蓝图

`内容选题表 → LLM 生成候选文案/配图提示词 → 规则检查（合规词、链接、重复度） → 人工审批 → 平台草稿箱/API 排程 → UTM/体验码批次 → 后台汇总 → LLM 周报与下周选题`。

首期建议只自动化“生成、检查、排程草稿、报表”，保留人工发布按钮。这样既节省运营时间，也避免账号风控、平台违规和品牌失控。
